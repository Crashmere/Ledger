# Architecture and Code Guide

See the [documentation entry point](README.md) for confirmed product boundaries and [OPERATIONS.md](OPERATIONS.md) for runtime maintenance. Agent-config's `server-operations` maintains the shared server design; this project does not duplicate global configuration.

## How Requests Flow

The browser first requests a page address. Go returns the embedded `index.html` and hashed JS/CSS. Vue Router mounts `/transactions` as the persistent workbench; `manage`, `add`, `batch`, and `txn/:id/edit` are child routes rendered in the side panel. The root path opens “明细”. Old `/overview`, `/search`, `/reports`, `/accounts`, and entry links redirect to the corresponding workbench view or panel while preserving applicable parameters; old search links default to all time. Go distinguishes only APIs, static resources, and page entry points; it does not render Vue page by page in the backend.

`router/lazyPage.ts` uses a synchronous route container for asynchronous page modules, so navigation completes and the title and selected item change immediately. `PageSkeleton` displays a placeholder while the module downloads and offers a reload action if the download fails. Skeletons cover metadata, initial results, and filter updates; failure exits the loading state and offers retry. The workbench keeps its background and filters mounted, and rereads data after a panel closes.

Workbench scrolling occurs in `.work-area`. Before `loading` changes from false to true and before the DOM updates, `Workspace` measures the old results container and immediately sets `min-height` to preserve its space. Removing the focused control after a pagination click triggers layout calculation, so the placeholder must be established before Vue replaces child nodes; waiting only for a parent style binding to update is insufficient. The style binding releases the height together with new content after loading. Consecutive switches share one preserved height, and stale requests cannot end loading early. `.work-area` disables browser scroll anchoring and retains the numeric scroll position when view content changes rather than anchoring to a result row. Page, page-size, view, and month changes do not call `scrollTo` or force the old position back after completion, so the user can still scroll while waiting. If new content is too short, the browser contracts to the natural boundary without permanent blank fill. Regression checks inspect actual pagination clicks, page-size changes, last-page boundaries, view/month switches, slow requests, rapid consecutive operations, and reduced-motion behavior frame by frame on desktop and a 375px phone.

The multi-application build sets `BASE_PATH=/ledger/`. Vue assets, routes, and APIs share this prefix. Shared Nginx accepts `/ledger/`, strips the prefix, and proxies to the Go service listening only on `127.0.0.1:18080`; other paths do not reach Ledger. It preserves `Host`, so same-origin validation still works behind the proxy.

Vue pages call explicit functions in `api/index.ts`. `client.ts` performs one `fetch` and parses errors; it does not automatically retry writes. HTTP handlers decode fixed JSON types and then call methods in the `ledger` package; only that package touches SQL. There is no repository-interface layer, ORM, event bus, or local ledger.

SQLite uses WAL, foreign keys, and one connection. Multi-step saves use transactions, while ordinary queries execute SQL directly. The count, current page, and daily subtotals for `transactions/query` are read in the same transaction. Statistics requested through separate interfaces may require refresh after another window writes, which is appropriate for the single-person use case.

A transaction's `amount` is always positive integer cents, while `type` distinguishes income, expenses, and transfers. A transfer occupies one row: `account_id` is the source and `to_account_id` the destination. Balances are calculated live from initial balances and all active transactions. Transfers do not add to global income or expenses.

Each category belongs to one account, and same-name categories may exist in different accounts. “洞察” merges by name; a single-account scope includes only that account's transactions, while the management panel edits by category ID.

`is_delete` marks only the three entity tables for accounts, categories, and transactions. Deleting a category explicitly removes references from active transactions; deleting an account first checks active categories and both ends of transactions. Archived accounts still permit entries. There is no database settings table; the browser retains only recent searches and display preferences.

## Walkthrough: Saving a Transaction

1. `AddTxn.vue` manages the form and numeric keypad. `expr.ts` evaluates short expressions, and `money.ts` converts amounts to cents.
2. `save` checks `saving` and constructs a complete `TransactionInput`. Editing and creation use the same fields, and dates send only `YYYY-MM-DD`. The native `SaveStatus` modal shows the wait state and makes the background unavailable. `useSaveGuard` blocks in-app back/navigation and asks the browser for a leave warning on refresh or close.
3. `txnService.create/update` uses asynchronous `fetch` and awaits the complete response without blocking the browser main thread. The user flow ends only after confirmation. The request timeout is 30 seconds, with no automatic retry. Explicit validation failures can return to the form for correction. When network interruption, response corruption, or service errors make the outcome unknown, the form is retained with a persistent prompt to inspect the ledger first, and that form cannot be submitted again.
4. `server.go` validates JSON, required fields, and request origin, then calls `Store.SaveTransaction`.
5. `transactions.go` validates amount, Beijing date, account, and category. On update, an unchanged date retains the original `time`.
6. The transaction and response entity are saved/read in the same database transaction. HTTP returns after commit; only then does the frontend clear the form or navigate back.

Batch entry reuses the same domain validation and `SaveStatus` wait screen. It blocks leaving and duplicate submission while saving and clears the batch only after confirmed success. An uncertain result must be verified before deciding what to do next. `batch.go` additionally parses each line's decimal amount and returns errors and totals; it revalidates the complete batch on confirmed save, and one invalid line rolls everything back.

Browser leave prompts cannot prevent the system from force-closing the App or terminating the browser. There is no persistent offline draft or automatic replay. When a save result is unknown, verification against the server ledger is authoritative.

## FabricWorld Integration

The server derives `fabricWorldEligible` in transaction responses when the active account name is “副业”, the owning category name is “纺织”, and type is `expense`. `AddTxn` automatically displays `FabricWorldSync` after successful creation; `SaveBatch` returns `fabricWorldTransactions`, which the batch page prompts in sequence. The `Workspace` transaction-detail dialog and `AddTxn` existing-transaction edit page display a “同步至 FabricWorld” button according to server eligibility and open the same dialog manually. The edit page compares the current form with the saved transaction; unsaved changes disable synchronization and instruct the user to save first. Manual synchronization does not submit the transaction form. Canceling or succeeding without navigation leaves the original detail view open, and repeated synchronization returns the existing fabric. Saving an edit does not automatically trigger synchronization; account/category renames are evaluated using the new names.

After the user agrees, the browser sends `POST /transactions/:id/fabricworld`. Ledger rereads the transaction from its own database and calls FabricWorld's `/api/integrations/ledger` through `LEDGER_FABRICWORLD_URL` (default `http://127.0.0.1:18082`). The browser cannot choose the target URL or override amount/name. The server-side HTTP timeout is 12 seconds, with no automatic retry.

FabricWorld uses the transaction ID as a persistent idempotency source and stores the date, total price converted from integer cents, and title. An empty title uses “未命名布料”. The fabric defaults to unused, one piece in one unknown-size group, with other details blank. Success returns the same-origin `/fabricworld/fabrics/:id/edit`. Retrying does not save the ledger transaction again, create a duplicate fabric, or overwrite details entered later. If the target fabric was deleted, the UI asks the user to verify or restore it. Later transaction edits/deletion do not automatically modify the fabric.

The synchronization dialog uses native `dialog` and blocks duplicate clicks and navigation while saving. A failed network synchronization can be retried manually, while ordinary transaction writes retain the rule against blindly retrying unknown outcomes. Each service keeps an independent database, release process, and backups; there is no cross-database transaction or continuous two-way synchronization.

Scripts write only to temporary data directories and listen locally on ports 19080–19082. They cover 320/375/1440px, new and existing transaction entry points, canceling, ineligible transactions, unsaved-edit protection, failures, response loss after commit, manual retry, repeated synchronization without resaving/recreating, field mapping, later photo/detail entry, and edit-page navigation. Screenshots are stored in ignored `var/fabricworld-verification`. The real phone system camera has not been automatically verified.

## Walkthrough: Filtering Transactions and Computing Statistics

1. `Workspace.vue` combines control state into `TransactionFilter`; keyword input uses a 180ms debounce. Temporarily excluded IDs also enter the filter. Keyword, fields, accounts, included/excluded categories, types, amount, sorting, and temporary exclusions are stored in route query parameters and restored after returning from an edit; the month reuses `useSelectedMonth` session state.
2. The same filter is passed separately to `query` and `summary`; `page`, `sortBy`, and `sortDir` affect only `query`.
3. `filters.go` builds the `WHERE` clause from fixed columns and parameterized SQL. Date ranges convert through Beijing time. Keywords use literal Unicode lowercase matching in title, note, and category. The amount field parses the keyword to integer cents and requires an exact match.
4. `transactions.go` uses `COUNT`, `ORDER BY`, and `LIMIT/OFFSET` for the current page. The workbench also requests complete daily subtotals for dates represented on that page.
5. `statistics.go` aggregates the full filtered set with SQL, then Go calculates annualized spending, fills missing dates, and assigns heatmap levels.
6. The frontend only draws, formats, and arranges the current page. Pagination does not rerequest statistics, while a filter change returns to page one. Request sequence numbers only prevent a late response from overwriting a newer choice.

The page selects `projectScope` explicitly; the backend does not recognize page names. Ledger and analysis default to `selected`: project accounts are excluded when no account is selected and included when selected explicitly. Choosing a normal account in the left rail or top bar defaults to the monthly range; choosing a project account defaults to all time. The shared time selector can always switch to month or another range. For one account, inflow, outflow, and net inflow include transfers on either end; global income and expenses exclude transfers.

Switching from “洞察” to “明细” shares the date range, account, amount, and keyword. Category drill-down adds the category and corresponding income/expense type; categories merge by name across accounts. The uncategorized row is statistics-only and does not create a jump missing a category condition. If the ledger receives a category name that no longer exists, it returns no results rather than allowing a stale link to expose every transaction.

## Connectivity and Maintenance Boundaries

APIs are not cached, and ledger entries are not stored in `localStorage` or a Service Worker. After disconnection is detected, page content is hidden and writes are disabled. A successful manual connection check reloads the list. There is no heartbeat, polling, or offline write queue.

`usePageRefresh` listens to window `focus`, page `visibilitychange`, and `ledger-reload`. It runs only while the page is visible, coalesces events arriving within 60ms, and does not start another request while one is active. When returning to the page, `Workspace` rereads accounts, categories, month bounds, and current-page statistics in the background while keeping existing content mounted and without setting page-wide `loading`. Background refresh reuses request sequence numbers and discards an old response after the user changes filters or pages. It is skipped while an entry/management panel, detail view, or synchronization dialog is open, during a foreground load, or while offline. Filter watchers observe only user conditions and date range—not refreshed category objects—so refresh neither resets the page nor causes an extra filter load. Identical JSON results reuse existing objects, preserving active trend/calendar hints when nothing changed. A failed background read retains existing results and offers retry. If only the daily chart fails, the last chart remains with an update-failed marker. Connection failure still enforces offline write blocking. Closing an entry/management panel uses the same background refresh: focus first returns to the opener with `preventScroll`, then data updates without replacing results with a skeleton. A foreground flow is used only if the workbench has never finished initial loading. Initial opening and genuine filter changes retain their existing foreground flow. Browser regressions cover frame-by-frame scroll/component stability on desktop and 375px, duplicate events, cross-window data changes, failure/retry, stale-request races, entry-draft protection, and closing a panel from both “明细” and “洞察” during a slow request without a skeleton or scroll movement.

`maintenance.go` provides native consistent backup, restoration to a new file, explicit upgrade-copy generation, and read-only checks. `schema.sql` creates version 2 with only accounts, categories, and transactions. `migrations/002_remove_tags.sql` deletes tags and transaction-association tables from a version 1 upgrade copy. `serve`/`check`/`backup` require version 2 and do not modify an old database automatically. `restore` preserves the source version, while `migrate` accepts only version 1 and creates a new version 2 file. See `OPERATIONS.md` for upgrades and rollback. Deployment uses systemd to start/stop the program; the NAS database is the only authoritative data source. NAS routine backups are manual full compressed captures on verified external storage, with native backup timers and automatic backup pruning disabled. Upgrades use complete root-private temporary protection under `/var/lib/server-upgrades/ledger/<release>/`, removed only after runtime and affected-data acceptance.

SQLite is embedded in the application and does not run as a separate database service. Each application owns an independent database file. Ledger's program, configuration, data, and backups live in separate subdirectories of `/opt/ledger`. Root manages the program and configuration; user `ledger` can write only its own `data` and `backups`.
